PHASE 3 (first cut — done today, 2026-09-26)
--------------
- New apps/apikeys app: ApiKey model (business-scoped, sha256-hashed
  secret, raw key shown exactly once at creation — same show-once idiom
  as Stripe/GitHub keys). ApiKeyAuthentication (DRF auth class, reads
  Authorization: Bearer <key> or X-API-Key) + HasApiKey permission set
  request.business/request.api_key, mirroring how IsBusinessMember does
  it for JWT dashboard requests.
- Public Chat API: POST /api/v1/public/chat/, authenticated by ApiKey
  (not JWT). Reuses the exact same _run_chat()/orchestrator.receive_message()
  pipeline as the playground — refactored PlaygroundChatView's body into
  a shared _run_chat() helper in apps/conversations/views.py so playground,
  public API, and widget chat can never drift into 3 different behaviors.
  Conversation.channel=API, rate-limited per-API-key (not per-IP) via
  custom ApiKeyRateThrottle (apps/apikeys/throttling.py).
- Website widget endpoints (public, no auth — Agent.public_widget_id was
  already reserved for this in Phase 1): GET
  /api/v1/widget/<widget_id>/config/ (name/greeting/tone/language only,
  nothing sensitive) and POST /api/v1/widget/<widget_id>/chat/
  (channel=WEBSITE, session_id becomes external_customer_ref). Rate-limited
  by IP via WidgetRateThrottle since there's no secret to key on.
- Usage tracking: UsageEvent model (apps.apikeys) logs one row per AI
  response across every channel — business, agent, api_key (nullable),
  channel, input/output tokens. GET /api/v1/usage/summary/ aggregates
  totals + breakdown by channel for the dashboard.
- New throttle scopes in settings: "public_api": "60/min", "widget": "20/min".
- Frontend: ApiKeysPage (frontend/src/pages/settings/ApiKeysPage.jsx) —
  create/list/revoke keys, one-time key reveal banner. Added to sidebar
  nav + routes. apiKeysApi.js service layer following existing pattern.
  `npm run build` verified clean.
- 12 new backend tests (apps/apikeys/tests, apps/conversations/tests/
  test_public_chat_and_widget.py) covering: key creation never leaks raw
  key on list, cross-tenant isolation on revoke, public chat rejects
  missing/invalid/revoked keys (403 — DRF default without a WWW-Authenticate
  header, not 401), cross-tenant agent access blocked, widget config is
  public/unauthenticated, widget chat creates a WEBSITE conversation and a

PHASE 3 continued (done today, 2026-09-27) — widget embed
--------------
- apps/core/static/widget/widget.js: standalone vanilla-JS embeddable
  chat widget (no framework/build step — a customer site just drops in a
  <script> tag). Floating bubble -> chat window, calls the existing
  GET .../widget/<id>/config/ and POST .../widget/<id>/chat/ endpoints.
  Session id persisted in localStorage, conversation id in sessionStorage
  (so a page reload keeps the same session but starts a fresh
  conversation, matching how the widget channel is meant to behave).
  Served automatically by Django's static file handling in dev
  (apps.core is in INSTALLED_APPS, AppDirectoriesFinder picks it up) —
  in prod this needs `collectstatic` + whatever serves STATIC_ROOT,
  same as every other static asset, nothing widget-specific to set up.
- apps/core/middleware.py: WidgetCorsMiddleware — the widget runs on
  arbitrary customer domains we can't put in CORS_ALLOWED_ORIGINS, so
  only requests under /api/v1/widget/ get a wildcard
  Access-Control-Allow-Origin (incl. answering the POST preflight
  directly, before it reaches DRF/auth). Every other endpoint keeps
  going through corsheaders' normal allow-list — verified with a test
  that GET /api/v1/agents/ does NOT get the wildcard header.
- Frontend: AgentFormPage now shows a "Embed on your website" card (only
  once an agent has been saved / has a public_widget_id) with the exact
  copy-pasteable <script> snippet, using apiClient's API_BASE_URL to
  build the widget's data-api-base.
- 3 new backend tests for the CORS middleware (wildcard on widget GET,
  preflight OPTIONS answered with 204 + wildcard, dashboard endpoints
  unaffected). 72/72 tests passing, frontend build clean.
- Phase 3 is now feature-complete per the original roadmap item (API
  keys, public Chat API, website widget, usage tracking, rate limiting)
  modulo the plan-tier/billing enforcement noted above, which was never

PHASE 4 (first cut — billing & subscriptions, done today, 2026-09-28)
--------------
- New apps/billing app, mirroring the apps.ai provider-abstraction pattern:
  - Plan model (code, price, per-plan limits: max_agents,
    max_messages_per_month, max_knowledge_documents, max_team_members —
    null = unlimited; nothing hard-coded, matches the "store limits in
    plan configuration" rule). Seeded via data migration
    (0002_seed_default_plans.py): starter (free, is_default=True),
    growth ($49/mo), scale ($199/mo, unlimited).
  - Subscription model (OneToOne on Business): status
    (trial/active/past_due/suspended/cancelled/expired), current period
    start/end, trial_ends_at, provider (manual/stripe/razorpay — only
    manual implemented), external_customer_id/external_subscription_id
    reserved for when a real gateway is wired up. Never deleted on
    lapse — status changes, row and any API keys stay intact, per the
    original spec ("do NOT delete the API key... authorization fails
    according to subscription status").
  - apps/billing/providers/: PaymentProvider ABC (start_checkout,
    cancel_subscription, verify_webhook_signature) + ManualPaymentProvider
    (only implementation right now — owner picks a plan, activates
    immediately, no real charge) + registry.get_payment_provider() as the
    single swap point for adding Stripe/Razorpay later without touching
    call sites.
  - apps/billing/signals.py: post_save on Business auto-starts a TRIAL
    subscription on the default plan (mirrors apps.leads' default-stage
    seeding signal exactly).
  - apps/billing/services.py: enforce_subscription_and_limits(business) —
    single chokepoint that checks subscription status is
    trial/active (else 402 SUBSCRIPTION_INACTIVE) and current-period
    usage against plan.max_messages_per_month (else 429
    USAGE_LIMIT_EXCEEDED, counted from the existing apps.apikeys
    UsageEvent table — no new usage-counting infra needed). Wired into
    apps/conversations/views.py _run_chat() so playground, public API,
    and widget chat are ALL gated identically — no channel can bypass
    billing via a different code path. activate_subscription() is the
    shared "turn a subscription on" function both the manual change-plan
    endpoint and a future payment-webhook handler will call.
  - Dashboard endpoints: GET /api/v1/billing/plans/ (public pricing),
    GET /api/v1/billing/subscription/ (current sub + usage this period,
    tenant-scoped), POST /api/v1/billing/subscription/change-plan/
    (owner/admin only, HasRole-gated — instantly switches plan via the
    manual provider).
  - Frontend: BillingPage (frontend/src/pages/billing/BillingPage.jsx) —
    current plan/status/usage bar, plan comparison cards with
    switch-plan buttons. billingApi.js service layer. Added to nav +
    routes. `npm run build` verified clean.
  - 10 new backend tests (apps/billing/tests/test_subscriptions.py):
    trial auto-starts on business creation, trial allows chat, suspended
    subscription blocks chat with 402 (verified through the real
    playground endpoint, not just the service function), usage-at-limit
    blocks with 429, activate_subscription switches plan/status,
    plan list is public, subscription detail includes live usage count,
    change-plan requires owner/admin role, subscriptions are tenant-
    isolated. 82/82 tests passing overall.
- NOT done yet from Phase 4 / Refinement 11+24 scope (deferred,
  documented as future work, not silently skipped):
  - No real Stripe/Razorpay integration — ManualPaymentProvider only.
    StripePaymentProvider/RazorpayPaymentProvider would implement the
    same PaymentProvider ABC; registry.py is the only place a new one
    needs registering.
  - No webhook receiver endpoint yet (nothing to receive from until a
    real gateway is wired up) — verify_webhook_signature() exists on the
    interface so this slots in without changing the interface shape.
  - No automatic period rollover (Celery beat job to renew

  - Refinement 12's "Redis for fast real-time usage checks" not done —

REFINEMENT 22 — REAL-TIME (WebSockets, done today, 2026-09-30)
--------------
- apps/conversations/ws_auth.py: JWTAuthMiddleware — Channels' stock
  AuthMiddlewareStack reads Django sessions, but this dashboard is
  JWT-authenticated, not session-authenticated, so a custom middleware
  was needed. A WebSocket handshake from browser JS can't set a normal
  Authorization header, so the access token travels as a `?token=` query
  param (same token already held in memory by apiClient); validated via
  SimpleJWT's AccessToken, resolves to a real Django user via
  database_sync_to_async.
- apps/conversations/consumers.py: ConversationConsumer — one Channels
  group per business ("business_<id>"). On connect, resolves the
  business from the authenticated user's active membership (mirrors
  apps.core.permissions.resolve_business_for_request — an optional
  ?business_id= query param may only narrow to one of the user's *own*
  memberships, never grant access to someone else's). Rejects with close
  code 4401 if unauthenticated or no membership. Push-only: the
  dashboard still drives all state changes through REST, the socket
  never accepts commands.
- apps/conversations/realtime.py: broadcast_message_created() and
  broadcast_conversation_updated() — thin wrappers around
  channel_layer.group_send(), no-op safely if no channel layer is
  configured. Wired into the shared apps.conversations.views._run_chat()
  (broadcasts the customer message immediately, then the AI message +
  updated conversation once the orchestrator responds — so this covers
  playground, public API, AND widget chat, not just the dashboard) and
  into ConversationTakeoverView / ConversationResolveView.
- config/asgi.py wraps the websocket router in JWTAuthMiddleware.
  apps/conversations/routing.py now actually registers
  ws/conversations/ (was an empty placeholder before today).
- config/settings/test.py: CHANNEL_LAYERS overridden to
  channels.layers.InMemoryChannelLayer for tests — base.py's real
  RedisChannelLayer would otherwise require Redis up just to run the
  test suite.
- Needed `daphne` (channels.testing.WebsocketCommunicator imports it
  transitively) — added to requirements.txt via pip freeze.
- Frontend: hooks/useConversationSocket.js — connects to
  ws://.../ws/conversations/?token=..., auto-reconnects after a fixed
  delay on close, and treats every inbound event as "go re-fetch via
  REST" rather than trying to patch state from the socket payload
  directly (the "after reconnect: REST fetch current state, then resume
  WebSocket" rule from the architecture doc — nothing here assumes a
  missed-while-disconnected event will ever be replayed). Wired into
  HandoffInboxPage: any message.created/conversation.updated event
  triggers a list re-fetch.
- 5 new backend tests (apps/conversations/tests/test_realtime.py) using
  channels.testing.WebsocketCommunicator: connect rejected with no
  token, connect rejected with an invalid token, connect accepted with a
  valid token + real membership, a real playground chat call (through
  the actual HTTP endpoint, not a mocked service call) delivers
  customer-message / ai-message / conversation-updated events in order
  to a connected socket, and a second business's socket receives nothing
  from the first business's chat (tenant isolation over WebSockets, not
  just REST). 90/90 tests passing overall, frontend build clean.
- NOT done yet: lead-update and generic notification events (only
  message/conversation events broadcast so far — leads/notifications
  apps don't call apps.conversations.realtime yet). No load-tested
  verification against real Redis — only the in-memory test layer.
  Conversation list page (frontend/src/pages/conversations, if a plain
  list view is later added beyond the Handoff inbox) isn't wired to the
  socket yet, only HandoffInboxPage is.
