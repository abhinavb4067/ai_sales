======================================================================
ROLE AND WORKING RULES
======================================================================

Act as the principal software architect, senior Django engineer, AI
engineer, security engineer, and technical lead for Ectama.

Your task is to build Ectama as a production-oriented, multi-tenant AI
Business Assistant SaaS. This is one unified platform through which many
independent businesses can create their own AI agents, provide business
knowledge, connect their websites, mobile applications, WhatsApp
Business accounts, and telephone systems, and automate customer support,
sales enquiries, lead qualification, appointments, follow-ups, and other
permitted business operations.

Before changing anything, inspect the existing repository, project
structure, dependencies, code conventions, environment configuration,
database schema, migrations, tests, and deployment setup. Reuse working
code where appropriate. Do not blindly overwrite, delete, rename, or
regenerate existing files. Do not assume that a feature exists without
inspecting it.

Work incrementally and preserve a coherent, runnable application. Do not
attempt to generate the entire system in one uncontrolled
code-generation pass. Implement the specification in milestones, run
checks and tests after each milestone, fix failures, and report exactly
what is complete, what is incomplete, what changed, and what requires
external credentials or manual setup. Do not claim a feature is complete
merely because files were generated.

When requirements are ambiguous, choose secure, maintainable defaults
and document the decision. Ask a question only when an essential
business or technical decision cannot safely be inferred. Never invent
API credentials, provider capabilities, legal approvals, or successful
external integrations.

====================================================================== 1.
PRODUCT VISION
======================================================================

Product name: Ectama Product category: AI Business Assistant and AI
Sales & Customer Communication SaaS.

The product must allow a business to:

1.  Register and create its own business workspace.
2.  Invite employees and assign roles.
3.  Create one or multiple AI agents.
4.  Configure each agent’s name, personality, language, tone,
    instructions, response style, business rules, tools, and model.
5.  Upload documents and add website sources.
6.  Connect approved external APIs and read-only external databases.
7.  Build a private business knowledge base.
8.  Select an AI provider and model.
9.  Choose Ectama-managed AI billing or bring their own provider API key
    (BYOK).
10. Generate secure API credentials and integrate an agent into their
    website or mobile app.
11. Install an embeddable website chat widget without needing to build a
    chat interface.
12. Connect their own WhatsApp Business account through the official
    Meta WhatsApp Business Platform.
13. Connect supported business telephone numbers through a suitable
    telephony/SIP provider.
14. Use the same AI agent across multiple channels.
15. View and manage conversations from one dashboard.
16. Capture leads, qualify enquiries, schedule appointments, arrange
    authorized callbacks, and hand over conversations to human
    employees.
17. View usage, costs, analytics, subscription information, and
    integration status.

The product must be suitable for many independent tenants and must never
expose one business’s data, credentials, conversations, knowledge,
customers, or usage to another business.

CORE PRODUCT PRINCIPLE: One shared Ectama AI orchestration engine serves
all tenants. Each tenant has strictly isolated data, agents, knowledge
bases, credentials, integrations, conversations, usage, and
configuration. One AI agent can be connected to multiple channels, and
all channels use the same central AI engine and business knowledge.

Do not create a separate AI application or separate codebase for every
customer. Use a shared, scalable application with strict tenant
isolation.

Start with a modular monolith, not microservices.

Keep one Django backend project, but organize business domains into
separate Django apps with clear boundaries. Keep provider-specific code
behind adapters and keep business logic out of views.

urls.py asgi.py celery.py apps/ accounts/ tenants/ memberships/

Adapt this structure to the existing repository instead of forcing a

Use: - UUID primary keys for public/domain entities. - created_at and

7. KNOWLEDGE MANAGEMENT AND RAG
======================================================================

A tenant can create multiple knowledge bases. An agent can be assigned
one or more knowledge bases. A knowledge base can contain multiple
sources.

Support sources: - PDF - DOCX - TXT - CSV - Other explicitly supported
document formats - Public website URLs - Manually entered business
information - Configured REST APIs - Restricted read-only external
database integrations

Implement domain entities equivalent to:

KnowledgeBase: - tenant - name - description - active status

AgentKnowledgeBase: - tenant - agent - knowledge base - unique
assignment constraint

KnowledgeSource: - tenant - knowledge base - source type - source name -
source configuration - status - last sync - last error -
version/fingerprint

Document: - source - original filename - object-storage location - MIME
type - size - processing status - checksum - metadata

DocumentChunk: - tenant - source/document - chunk index - text content -
embedding - embedding model identifier - metadata - source location/page
reference

KnowledgeSyncRun: - source - status - start/end timestamps - processed
count - failure details

RAG pipeline: 1. Validate and securely store upload. 2. Extract text in
a background worker. 3. Normalize and clean content. 4. Split text into
configurable chunks with overlap. 5. Generate embeddings through a
provider abstraction. 6. Store vectors in pgvector. 7. Record source
metadata and version. 8. Retrieve relevant chunks for a customer query.
9. Apply tenant and knowledge-base filters inside the database retrieval
query. 10. Build a grounded AI context. 11. Return an answer with an
appropriate fallback when evidence is insufficient.

Use pgvector VectorField, not JSON, for production similarity search.
Ensure vector dimensions match the selected embedding model. If multiple
embedding dimensions are needed, use separate compatible tables/indexes
or another explicit dimension-aware architecture. Keep embedding model
and version metadata. Do not mix incompatible vector dimensions.

Use a consistent initial embedding model across tenants if that
simplifies indexing, independently of their selected chat model. Make
re-embedding possible when the embedding model changes.

Website ingestion: - Crawl only permitted public pages. - Respect
robots.txt and reasonable crawl limits. - Deduplicate URLs and
content. - Track changed content. - Support scheduled sync. - Prevent
SSRF, DNS rebinding, access to localhost, private IP ranges, cloud
metadata endpoints, and internal services. - Restrict redirects, ports,
response sizes, content types, and timeouts. - Do not crawl
authenticated/private pages unless a specifically authorized integration
is designed for them.

External API integrations: - Only call configured and authorized
endpoints. - Store credentials securely. - Use allowlisted hosts and
safe network egress. - Apply timeouts, response-size limits, rate
limits, and schema validation. - Do not let the AI invent arbitrary URLs
or send credentials to arbitrary hosts.

External database integrations: - Use dedicated read-only credentials. -
Restrict network access. - Use statement timeouts and row limits. -
Allow only approved tables/views and parameterized queries. - Never
execute arbitrary AI-generated SQL. - Never connect customer databases
to Ectama’s primary database using privileged credentials.

Treat retrieved documents and external content as untrusted data, never
as system instructions. Defend against prompt injection and malicious
content.

12. VOICE AND TELEPHONY
======================================================================

Build voice as a separate real-time channel adapter using a supported
voice AI provider and SIP-compatible telephony provider.

Potential AI: - OpenAI Realtime API - Other providers behind a common
voice interface where supported

Potential telephony: - A suitable SIP or licensed telecom provider,
selected after verifying country coverage, number provisioning,
inbound/outbound support, and applicable regulations.

Support two distinct workflows:

INBOUND: 1. Customer calls the business number. 2. Telephony provider
routes the call to Ectama. 3. Ectama verifies the called
number/connection and resolves tenant and agent. 4. Establish
low-latency real-time voice session. 5. AI listens and responds using
the same business knowledge and permitted tools. 6. AI may capture lead
information, answer questions, schedule an appointment, or request human
transfer. 7. Save call metadata, events, summary, and permitted
transcript/recording.

OUTBOUND: 1. Business selects or schedules an eligible customer
callback. 2. Verify the business is authorized to call and the customer
has the required consent. 3. Apply country-specific calling
restrictions, time windows, suppression lists, frequency limits, and
provider rules. 4. Initiate the call through an approved provider. 5. AI
conducts the conversation. 6. Save call events, result, summary, and
permitted transcript/recording. 7. Update lead status and follow-up
actions.

Implement: - CallSession - CallEvent - ProviderCallReference - call
state machine - inbound/outbound direction - tenant and agent binding -
provider adapter - real-time session handling - call transfer - call
summaries - transcript/recording metadata - recording consent -
retention controls - usage metering - error and retry handling

Do not process real-time audio through slow ordinary HTTP
request/response tasks. Use the provider’s supported real-time
streaming/SIP architecture. Keep voice transport independent from the
normal background message queue.

India-specific requirements: - Do not assume an international virtual
number provider permits unrestricted calls to Indian numbers. - Verify
current Indian telecom provider eligibility and licensing. - Investigate
applicable TRAI, DLT, commercial communication, consent, caller
identity, numbering, recording, and data protection requirements with
qualified compliance guidance. - Do not enable commercial outbound
telecalling until the applicable provider and legal requirements have
been verified. - Never initiate calls without the required business
authorization and customer consent.

19. SECURITY, PRIVACY, AND RELIABILITY
======================================================================

Security is a core product requirement, not a final optional task.

Implement and test:

TENANT ISOLATION: - Every tenant-owned record has tenant ownership. -
Every query and mutation verifies tenant access. - Related objects must
belong to the same tenant. - Retrieval queries must filter tenant and
assigned knowledge base in the database. - Add cross-tenant security
tests for every major resource. - Use PostgreSQL RLS where practical as
defence in depth.

SECRETS: - Encrypt provider credentials and channel tokens. - Use
KMS/envelope encryption where possible. - Keep master encryption keys
outside the database and source repository. - Rotate secrets where
supported. - Redact secrets from logs and error messages.

FILES: - Validate file extension, MIME type, signature, size, and
content. - Store files outside the public web root. - Use malware
scanning where practical. - Use signed, short-lived download URLs. -
Prevent path traversal and unsafe file parsing.

WEBHOOKS: - Verify provider signatures. - Validate timestamps/state
where supported. - Use idempotency keys and unique provider event IDs. -
Handle retries and out-of-order events. - Never trust unverified webhook
payloads.

AI: - Treat uploaded and retrieved content as untrusted. - Defend
against prompt injection. - Do not expose hidden system instructions or
other tenants’ data. - Validate tool calls server-side. - Apply tool
allowlists and authorization. - Limit output, context, tool loops, time,
and spending. - Provide a safe fallback when knowledge is
insufficient. - Do not fabricate business facts, prices, availability,
or completed actions.

EXTERNAL NETWORK: - Prevent SSRF and access to internal/private network
resources. - Restrict allowed hosts and ports. - Validate DNS and
redirects. - Apply timeouts and response-size limits. - Use safe egress
policies.

PRIVACY: - Collect only necessary customer information. - Provide
configurable retention and deletion. - Protect exports. - Avoid storing
sensitive data unnecessarily. - Support consent and opt-out
preferences. - Define recording/transcript retention. - Follow
applicable data protection and communication requirements.

RELIABILITY: - database backups and tested restores - health checks -
structured logs - error monitoring - queue monitoring - database
connection management - graceful provider failure - rate limits - load
tests - disaster recovery documentation

Every screen, API, and workflow in this specification must support this
journey end-to-end without requiring Ectama staff to manually provision
a tenant, agent, channel, or subscription on the customer's behalf.
Manual/Django-admin-only setup paths are acceptable only for Super Admin
operational tasks (platform health, abuse response), never for a step a
paying customer is expected to complete themselves.

Super Admin dashboard should be separately permission-protected.

Use consistent UI components, loading states, empty states, error
states, validation, responsive layouts, and accessible controls. Do not
expose private provider credentials or internal tenant data in frontend
state unnecessarily.

21. API DESIGN
======================================================================

Use versioned routes under /api/v1/.

Suggested route groups:

/auth/ /tenants/ /memberships/ /agents/ /ai/providers/ /ai/models/
/ai/credentials/ /knowledge/bases/ /knowledge/sources/
/knowledge/documents/ /integrations/ /chat/ /conversations/ /channels/
/channels/whatsapp/ /voice/ /leads/ /customers/ /appointments/
/api-keys/ /webhooks/ /usage/ /billing/ /analytics/ /admin/

Use consistent: - serializers and validation - pagination - filtering -
ordering - error formats - authentication - permissions - rate limits -
API documentation

Separate dashboard APIs from public developer APIs where their
authentication and permissions differ.

Generate OpenAPI documentation using drf-spectacular or an equivalent
maintained tool.

22. TESTING AND ACCEPTANCE REQUIREMENTS
======================================================================

Write automated tests throughout development, not only at the end.

Test: - user registration and login - tenant creation - multiple
memberships - role permissions - agent creation and configuration -
provider selection - BYOK credential isolation - document ingestion -
vector retrieval - tenant-filtered retrieval - website crawling
security - external API security - tool authorization - API key
generation and revocation - website widget API - webhook signature
validation - webhook idempotency - WhatsApp message routing -
conversation isolation - human handover - lead creation - appointment
conflicts - voice call state transitions - consent checks - usage
recording idempotency - payment verification - rate limiting -
background task retries

Mandatory cross-tenant tests: - Tenant A cannot read Tenant B’s
documents. - Tenant A cannot search Tenant B’s knowledge. - Tenant A
cannot read Tenant B’s conversations. - Tenant A cannot use Tenant B’s
credentials. - Tenant A cannot use Tenant B’s channel connections. -
Tenant A cannot modify Tenant B’s leads or appointments. - A public
widget key cannot access private APIs. - A revoked API key cannot
authenticate. - A duplicate webhook event cannot create duplicate
messages or actions.

Use unit, integration, API, security, and realistic end-to-end tests.
Mock external providers in automated tests, and provide a separate
manual integration test guide for real provider credentials.

======================================================================
24. DEFINITION OF A WORKING MVP
======================================================================

The first MVP is complete only when all of the following work
end-to-end:

1.  A business can register.
2.  The business gets its own isolated workspace.
3.  The business can create an AI agent.
4.  The business can select OpenAI or Gemini.
5.  The business can upload a PDF.
6.  Ectama processes the document and stores searchable embeddings.
7.  The business can test the agent.
8.  The business can generate a restricted website integration key.
9.  The business can install the website chat widget.
10. A real website visitor can ask a question.
11. The AI retrieves the correct tenant’s business information.
12. The AI sends a relevant response through the widget.
13. The conversation is saved and visible in the business dashboard.
14. A second business can independently create an agent and use the
    system.
15. Automated tests prove that the second business cannot access the
    first business’s data or credentials.

WhatsApp, CRM automation, and voice calling are subsequent milestones.
Do not mark them as complete until tested against real provider
sandboxes or approved production integrations as appropriate.

======================================================================
25. DEPLOYMENT AND OPERATIONS
======================================================================

Provide reproducible development and production environments.

Use Docker Compose for local development with: - Django application -
ASGI application - Celery worker - Celery scheduler where needed -
Redis - PostgreSQL with pgvector - Nginx where appropriate

Production should use: - HTTPS - Nginx/reverse proxy - separate web and
worker processes - secure PostgreSQL - Redis protected from public
access - private object storage - environment/secrets management -
database backups - tested restore process - structured logs - monitoring
and alerting - health checks - deployment and rollback instructions

Do not expose PostgreSQL, Redis, internal admin endpoints, or worker
management interfaces publicly.

Document environment variables in an example file with placeholders
only. Never commit real credentials, API keys, tokens, private
certificates, or production database passwords.

======================================================================
FINAL PRODUCT GOAL
======================================================================

Build Ectama as a secure, scalable, multi-tenant AI Business Assistant
SaaS where a business registers once, creates and configures its AI
agent, selects its AI provider, supplies business knowledge through
documents, websites, and authorized external systems, and connects that
same agent to its website, mobile application, WhatsApp Business
account, and supported telephone system.

The same central AI engine must understand the business’s information,
maintain channel-appropriate conversation context, answer customer
questions, retrieve live business data through authorized integrations,
capture and qualify leads, schedule appointments, arrange permitted
callbacks, and hand over conversations to human employees.

The platform must isolate every tenant’s data and credentials, meter
usage accurately, enforce subscription limits, provide a clear business
dashboard and developer API, and be maintainable by a small engineering
team.

Start by inspecting the existing repository and reporting its current
structure, technology stack, completed functionality, missing
functionality, and any risks. Then propose the exact implementation plan
for MILESTONE 1. Do not make destructive changes before reporting the
inspection findings and obtaining authorization if a change would
overwrite or remove existing work.
